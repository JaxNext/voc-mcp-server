# 1.5 — `OAuthProvider` around `/mcp` (Task 5) Implementation Record

> Task 5 of [implementation-plan.md](implementation-plan.md), built against
> [tech-design.md](tech-design.md) §3.1/§7.1/§7.2/§7.3/§8/§10/§11/§14 R1.
> **Date:** 2026-09-30.
> **Status:** code complete and verified by tests + a running `wrangler dev`.

**Goal:** MCP clients can discover, register and call the server (§7.1, §7.2). This is the
**outer** OAuth flow: `@cloudflare/workers-oauth-provider` is the Authorization Server to MCP
clients, and `/mcp` is its protected `apiRoute`. It is the layer that finally wraps the Task 4
`defaultHandler` (Worker-as-Voc-client) and gives the six tools an authenticated identity.

## What was built

```
│   ├── index.ts              # entry module: `export { default } from './provider'` only
│   ├── provider.ts           # NEW — OAuthProvider + RESOURCE/ALLOWED_HOSTNAMES + session factory + apiHandler
│   ├── auth/handler.ts       # (Task 4) became the provider's defaultHandler
│   ├── auth/token-store.ts   # (Task 4) KV custody keyed by voc_user_id
│   └── mcp/…                 # (Tasks 2–3) createServer + six tools, unchanged
└── test/
    └── oauth-provider.spec.ts  # NEW — 7 tests
```

Design choices worth noting:

- **The wiring lives in `src/provider.ts`, not the entry module.** workerd validates the
  entry module's named exports as worker entrypoints; a plain value export (`RESOURCE`, an
  array) aborts startup. `src/index.ts` is therefore a one-liner re-export, and every other
  export lives in `./provider`.
- **`apiHandler` is an object wrapper, not a bare handler.** The provider's `validateHandler`
  requires an `apiHandler` that is an object with `.fetch`, and it dispatches with
  `fetch(request, env, ctx)`. The wrapper builds `createMcpHandler(() => createServer(factory),
  { allowedHostnames })` per request and forwards all three args, so `ctx.props` — set by the
  provider from the decrypted grant — reaches the MCP handler.
- **Identity flows props → KV, never a tool argument.** The provider attaches grant props to
  the request; the MCP handler surfaces them as `getMcpAuthContext().props`. The session
  factory reads `props.voc_user_id` and loads the live Voc credential from `VOC_SESSIONS`.
  Neither the identity nor the credential is ever a tool parameter (§8, §10).
- **Missing identity fails loudly.** If `props.voc_user_id` is absent or the KV session is
  missing, the factory throws an explicit "reconnect the MCP client to Voc" error which the
  tools turn into an `isError` result (§7.3, §9) — never an empty success.
- **Dev constants are quarantined.** `RESOURCE = 'http://localhost:8787'` and
  `ALLOWED_HOSTNAMES = ['localhost']` are dev values with comments marking Task 7 as the owner
  of the deployed hostname. `http://localhost:8787` is accepted by the provider (plain http on
  a loopback host) and its origin-only audience matches requests to `/mcp`.
- **DCR only.** `clientRegistrationEndpoint: '/register'`; CIMD stays off
  (`client_id_metadata_document_supported: false`), per §14 **R1**. The runtime warning
  `CIMD (Client ID Metadata Document) is disabled` is expected and benign.
- **`accessTokenTTL` = 30 days.** The client's token gates nothing but this Worker — the real
  credential is the Voc token in KV — so a long TTL is safe and avoids needless re-consent
  (§7.3).

## Issues hit and how they were resolved

### 1. `wrangler dev` aborted: entry-module named-export validation

First version kept `RESOURCE`/`ALLOWED_HOSTNAMES` as named exports in `src/index.ts`. `wrangler
dev` refused to start:

```
✘ [ERROR] service core:user:voc-mcp-server: Uncaught TypeError:
  Incorrect type for map entry 'RESOURCE': the provided value is not of type
  'function or ExportedHandler'.
```

**Cause:** workerd treats an entry module's named exports as worker entrypoints, each of which
must be a function or an `ExportedHandler`. A `string`/`string[]` export is invalid.

**Fix:** moved the provider and all its supporting values into a new non-entry module
`src/provider.ts`; `src/index.ts` now only `export { default } from './provider'`. The test
imports the constants from `../src/provider`.

### 2. `/mcp` returned 403 instead of 200 in the e2e test

`createMcpHandler({ allowedHostnames })` rejected the request with
`{"jsonrpc":"2.0","error":{"code":-32000,"message":"Missing Host header"}}` (SDK
`hostHeaderValidationResponse`). A `Request` constructed in the Workers test pool carries no
`Host` header, but the MCP handler's DNS-rebinding allowlist requires one.

**Fix:** the test sets `Host: new URL(url).host` explicitly (in both `callMcp` and the e2e
`/mcp` request). This mirrors what a real client sends and does not weaken the check.

### 3. `apiHandler` must be an object

`apiHandler: createMcpHandler(…)` (the runtime *function* returned by the factory) fails the
provider's `validateHandler` (`typeof handler === 'object'` is required) and would never
receive `ctx`. **Fix:** wrapped it as `vocApiHandler = { fetch(request, env, ctx) { … } }` and
pass the three arguments through. Constructor-time type check via `OAuthProvider<Env>` keeps
`env` typed.

### 4. `env.OAUTH_PROVIDER` must exist at construction

`OAuthProvider` persists grants in a KV namespace bound as `OAUTH_PROVIDER` on `env`; the
binding is already present from Task 1. No change needed, but noted because the e2e test
depends on it (real KV via `cloudflare:test`).

## Deviations from the design doc

| § | Design said | Actual | Reason |
|---|---|---|---|
| §8 shape | `apiHandler: createMcpHandler(createServer)` | object wrapper `{ fetch(request, env, ctx) }` around the handler | the provider validates `apiHandler` as an object with `.fetch` and dispatches with 3 args; the wrapper forwards `ctx` so `ctx.props` reaches the MCP handler |
| §8 shape | wiring in `src/index.ts` | wiring in `src/provider.ts`; `src/index.ts` re-exports the default | workerd validates the entry module's named exports as entrypoints — value exports abort startup |
| §8 identity | "`authInfo.props` carries `voc_user_id`" | read via `getMcpAuthContext().props` | `workers-oauth-provider` does not expose an `authInfo` type; the MCP handler surfaces the provider-set `ctx.props` |
| §10 | `allowedHostnames` = deployment hostname | dev value `['localhost']` (`ALLOWED_HOSTNAMES`) | the real hostname is only known from Task 7's deploy; comment marks Task 7 as owner |
