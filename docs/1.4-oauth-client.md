# 1.4 — Worker as an OAuth Client of Voc (Task 4) Implementation Record

> Task 4 of [implementation-plan.md](implementation-plan.md), built against
> [tech-design.md](tech-design.md) §3/§7/§8/§11. **Date:** 2026-09-29.
> **Status:** code complete and verified by tests — but the browser walk-through exit

**Goal:** the browser flow of §3 ends with a Voc token in KV (§7.3). This is the **inner**
OAuth flow: inside the `OAuthProvider`'s `defaultHandler`, the Worker acts as an OAuth
**client** of Voc/Supabase — a second authorization-code + PKCE hop ending at `/callback` —
so a single connection makes the user consent **twice** (§3).

Design choices worth noting:

- **Two roles, one Worker.** `workers-oauth-provider` is the **authorization server** to MCP
  clients (`/authorize`, `/token`, `/register`, discovery, PKCE, DCR). Its `defaultHandler`
  (this task) is simultaneously an OAuth **client** of Voc. The user sees two consent
  screens; only the second is Voc's.
- **`token-store.ts` is deliberately dumb** — get/put/delete of the credential set
  `{ refresh_token, access_token, expires_at, scope }`. No refresh logic: that is Task 6.
  Keeping it free of policy makes the custody contract (§7.3) trivially auditable.
- **Props are identity, never credentials.** Grant props are write-once in
  `workers-oauth-provider` and cannot rotate, so they carry only
  `{ voc_user_id, voc_email }` (`VocGrantProps`). The rotating credential set lives in
  `VOC_SESSIONS` under `voc_user_id`. `/callback` writes KV **and** the grant from the same
  identity, so a caller on `/mcp` reads `authInfo.props.voc_user_id` → KV (§7.3).
- **Public client, no secret.** The code exchange authenticates with `client_id` +
  `code_verifier` and `auth_method: 'none'` (§7.2). There is no client secret anywhere.
- **`offline_access` or fail loudly.** Without it Voc issues no refresh token and the user
  would re-consent hourly (§7.5). `exchangeCodeForTokens` treats a token response with an
  empty `refresh_token` as a **502**, not a silent success storing a dead session.
- **Errors are pages, not empty success** (§7.3, §9): every `/callback` failure renders a
  recovery page telling the user to restart the connection from their MCP client.
- **`fetchImpl` seam.** `createVocAuthHandler({ fetchImpl })` routes the two Supabase calls
  through an injectable fetch. Production uses the global `fetch`; the test injects a stub so
  the **real** `OAuthProvider` and **real** (simulated) KV run with only Supabase faked.
- **CSRF = double submit.** `/authorize` sets `__Host-CSRF_TOKEN` (Secure; Path=/; HttpOnly;
  SameSite=Lax) and embeds the **same** token in the consent form; the POST acts only if they
  match. The provider's own browser-bound consent handle adds a second layer.

## Issues hit and how they were resolved

### 1. `OAuthProvider` throws without an API route

Constructing `new OAuthProvider({ defaultHandler, … })` in the test threw
`TypeError: Must provide either apiRoute + apiHandler OR apiHandlers. No API route
configuration provided.` (oauth-provider.js:2075). Task 4 only exercises the `defaultHandler`
path, but the constructor validates the API-route config unconditionally. Fixed by giving the
test's provider an inert `apiRoute: '/mcp'` + `apiHandler: { fetch: async () => new
Response('ok') }`; the real `/mcp` handler is Task 5's job.

### 2. CSRF token generated twice — consent POST always 403

The first version of `authorize()` called `randomToken()` once for the hidden form field and
again for the `Set-Cookie`. They never matched, so every approve returned
`403 CSRF check failed`. Fixed to compute the token once and use it for both (handler.ts).

### 3. `/token` returned `401 invalid_client`

`getOAuthApi().createClient({ redirectUris, clientName })` defaults
`tokenEndpointAuthMethod` to `client_secret_basic` (a confidential client with a generated
secret), so a public-client `/token` call with PKCE and no secret failed at
`oauth-provider.js:2579`. Fixed by registering the test client as
`tokenEndpointAuthMethod: 'none'` — which is also what real MCP clients are (PKCE, no shared
secret). That made the provider enforce PKCE on `/authorize` (line 142), so the two
non-`approveConsent` tests had to send `code_challenge`/`code_challenge_method` too; both now
share an `authorizeUrlFor()` helper.

### 4. `cloudflare:test` types and `fetchMock`

`cloudflare:test` would not resolve until `tsconfig.json` `types` gained
`"@cloudflare/vitest-pool-workers/types"`. `fetchMock` no longer ships with
`@cloudflare/vitest-pool-workers` 0.22.0, so the Supabase stub is injected at the handler's
`fetchImpl` seam instead — a higher-fidelity test than mocking global fetch, and it forced the
handler to have a clean seam.

### 5. `env` import is deprecated in favour of `cloudflare:workers`

The suite still passes `env as poolEnv` from `cloudflare:test` with a cast to `Env`; the pool
logs no error, and `reset()` per test clears `OAUTH_KV` + `VOC_SESSIONS`. Noted for a later
cleanup, not blocking.

1. **Manual Supabase registration** (implementation-plan Task 4, §7.4). In Supabase →
   Authentication → OAuth Apps create `Voc MCP Server (dev)`, type **public**, redirect URI
   `http://localhost:8787/callback` (exact, no wildcards), and put its `client_id` in
   `.dev.vars` as `VOC_OAUTH_CLIENT_ID` (currently the placeholder `TODO-task-4`). Do **not**
   reuse the existing test client `9b5a1ba3-…` (redirect `http://localhost:3000/callback`).
2. **The browser walk-through** itself. It cannot be run from Task 4 alone: nothing dispatches
   `/authorize`/`/callback` yet — the `OAuthProvider` that does is wired in
   [Task 5](implementation-plan.md). Once Task 5 lands and `VOC_OAUTH_CLIENT_ID` is real,
   point a browser (or Claude's custom connector) at `/authorize` and confirm both consents
   complete and `VOC_SESSIONS` holds a Voc token.
