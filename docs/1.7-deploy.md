Design choices worth noting:

- **One artifact, request-derived origin.** `OAuthProvider` bakes `resourceMetadata.resource` at
  construction and validates it then (absolute HTTPS, or `http` on loopback only), so an
  origin-dependent `resource` needs an origin-dependent instance. Rather than shipping two
  configs, the Worker reads the origin off the incoming request (`new URL(request.url).origin`)
  and memoises an `OAuthProvider` per origin. The RFC 9728 `resource`, the
  `WWW-Authenticate` metadata URL, and the AS issuer all fall out of the same origin, so **the
  same artifact is correct under `wrangler dev` and in production**. This mirrors the library's
  own `getAuthorizationServerIssuer(requestUrl)` behaviour.
- **No `[env.*]` split.** `wrangler.jsonc` `vars` holds the *production* pair (what `deploy`
  ships); `.dev.vars` holds the *dev* pair and wins over `vars` for `wrangler dev` **and** the
  vitest pool. One config serves both. Empirically verified (see below).
- **`allowedHostnames` omitted on purpose.** Left unset, the MCP SDK applies its own default —
  the loopback set under `wrangler dev`, the request hostname on `*.workers.dev` — which keeps
  one artifact host-validated in both places. Hard-coding a single hostname would break one of
  them.
- **`VOC_SUPABASE_ANON_KEY` is a secret, never a var.** It is the publishable key sent as
  `apikey` on PostgREST calls; it lives in `.dev.vars` locally and via `wrangler secret put` in
  production (§8).

## Issues hit and how they were resolved

### 1. A static `resource` / `allowedHostnames` cannot be right in both environments

The Task 5 code pinned `RESOURCE = 'http://localhost:8787'` and
`ALLOWED_HOSTNAMES = ['localhost']` as module constants, with a note that "Task 7 replaces it
with the deployed hostname". But `wrangler.jsonc` and the provider instance are per-environment
while the artifact is single: a literal prod hostname would brick dev, and a literal dev hostname
would be wrong live.

**Fix:** derive both from the request origin. `originOf(request)` feeds `bearerChallenge(origin)`
and `providerFor(origin)`; `allowedHostnames` is dropped entirely so the SDK default applies.
This is the only option of the four considered (hardcode prod / env var + lazy provider /
`[env.production]` / request-derived origin) that keeps a single artifact correct in both places,
and it is the one the library itself models internally.

### 2. workerd rejects non-handler named exports in the entry module

`src/index.ts` is `export { default } from './provider'`. workerd validates the entry module's
named exports as worker entrypoints, so the `RESOURCE` string and `ALLOWED_HOSTNAMES` array had
to live in `src/provider.ts` (not the entry module) — unchanged from Task 5, but the reason the
origin helpers sit in `provider.ts` too.

### 3. Bare `OAuthProvider` default export vs. a request-dependent instance

The default export had to become an `ExportedHandler` **object** (`{ fetch(request, env, ctx) }`)
rather than a bare provider instance, so the origin can be read from the request *before* the
provider is constructed. `src/index.ts`'s `export { default }` is unaffected.

### 4. The local network blocks the deployment

`curl` to the deployed URL timed out (`curl: (28)`); `host` resolved the workers.dev name to a
Dropbox IP (`162.125.80.5`) and `dig` timed out — the environment poisons/blocks `workers.dev`
DNS. `api.cloudflare.com` stayed reachable (403 unauthenticated).

**Fix:** found a local HTTP proxy at `127.0.0.1:7890` (probing 7890/1087/8080/10809/8888) and ran
all verification curls with `https_proxy=http://127.0.0.1:7890`. `wrangler deploy` / `wrangler dev`
themselves were never affected.

### 5. `wrangler tail` cannot stream here

`wrangler tail` (both `--format pretty` and `--format json --status ok`) produced **no output at
all** — not even the connecting banner — even with requests in flight, so the tail websocket
endpoint is blocked by the same network. Accepted as an environment limitation; partial log-safety
evidence recorded instead (see below).

### 6. First deploy shipped the wrong OAuth pair

The first `wrangler deploy` (version `1b1ec5f0-…`) ran *before* `wrangler.jsonc` was switched to
production values, so the live Worker still carried the dev client id and the localhost callback —
the Voc leg was non-functional.

**Fix:** after the production client id and anon secret were in place, `wrangler secret put` +
`wrangler deploy` again → version `3dad11e4-…`. The deploy output now lists
`env.VOC_OAUTH_CLIENT_ID ("cde8bf9e-…")`.

### 7. `.dev.vars` precedence (verified, not assumed)

Two independent checks confirmed `.dev.vars` wins over `wrangler.jsonc` `vars`: (a) `wrangler dev`
printed `env.VOC_OAUTH_CLIENT_ID ("(hidden)")` / `env.VOC_REDIRECT_URI ("(hidden)")` — hidden
because they come from `.dev.vars` — while `VOC_SUPABASE_URL` showed its literal value; (b) a live
dev DCR → authorize → consent flow emitted an upstream redirect with
`redirect_uri=http://localhost:8787/callback` + `client_id=3c1d4c57-…`, i.e. the **dev** pair, not
the production values in `wrangler.jsonc`.
