## Issues hit and how they were resolved

### 1. pnpm 12 blocks dependency build scripts

`pnpm add` failed with `ERR_PNPM_IGNORED_BUILDS` for `esbuild`, `core-js-pure` (and later
`workerd`). Two traps here:

- The classic `pnpm.onlyBuiltDependencies` field in `package.json` is **dead in pnpm 12**
  (explicit warning: *"the pnpm field in package.json is no longer read"*).
- The setting moved to `pnpm-workspace.yaml` and was **renamed**: pnpm 12 calls it
  `allowBuilds` (a map of `package: true|false`), not `onlyBuiltDependencies`
  (see <https://pnpm.io/settings/build>).

Resolution — `pnpm-workspace.yaml`:

```yaml
packages: []

allowBuilds:
  esbuild: true
  core-js-pure: true
  workerd: true
```

`workerd` must stay on this list: its postinstall wires the runtime binary that
`wrangler dev` and the test pool both execute.

### 2. Latest wrangler was uninstallable; pinned to pool-workers' exact pair

The first dev-deps install failed with `ERR_PNPM_NO_MATCHING_VERSION`:
`wrangler@latest` (4.143.0) pins `workerd@1.20260926.1`, which the registry initially
reported as unpublished (latest shown: `1.20260924.1`). Meanwhile
`@cloudflare/vitest-pool-workers@0.22.0` pins **exact** versions of its own toolchain:
`wrangler 4.124.0` + `miniflare 5.20260815.0-alpha`.

Resolution: install `wrangler@4.124.0` — exactly what pool-workers pins — so the CLI, the
test pool, and miniflare share one dependency set. (The registry metadata later listed
`1.20260926.1` as published, so the failure was partly stale metadata; the pin decision
still stands, because pool-workers pins its wrangler exactly and a mixed pair buys nothing.)

### 3. `@cloudflare/vitest-pool-workers/config` no longer exists

`defineWorkersConfig` / `defineWorkersProject` are gone in 0.22.0 — the package's export map
is only `.`, `./types`, and a v3→v4 codemod. The shipped codemod
(`dist/codemods/vitest-v3-to-v4.mjs`) defines the target shape: the pool becomes a **Vitest
plugin**.

Resolution — `vitest.config.ts`:

```ts
import { cloudflareTest } from '@cloudflare/vitest-pool-workers'
import { defineConfig } from 'vitest/config'

export default defineConfig({
  plugins: [cloudflareTest({ wrangler: { configPath: './wrangler.jsonc' } })],
})
```

### 4. The design's compatibility date is above the test runtime's ceiling

First test run: `ERR_RUNTIME_FAILURE`, with workerd's own log line naming the cause —
*"This Worker requires compatibility date `2026-09-01`, but the newest date supported by
this server binary is `2026-08-22`."* pool-workers 0.22.0 pins a runtime from mid-August;
the design's §8 date of 2026-09-01 postdates it.

Resolution: `compatibility_date: "2026-08-22"` everywhere (dev, test, deploy share one
date; nothing the server uses is gated between 08-22 and 09-01 — the MCP 2026-07-28 spec is
protocol-level, not a Workers flag). Recorded in `wrangler.jsonc`, tech-design §8, and the
plan's Task 1. **Follow-up: bump the date when pool-workers ships a newer runtime — the
comment in `wrangler.jsonc` says so at the site.**

### 5. wrangler/workerd need their state directory

`wrangler dev` and the vitest pool both write logs and runtime state to
`~/Library/Preferences/.wrangler` and spawn local workerd processes. Runs must happen with
access to that path (agent-sandbox runs fail with `ERR_RUNTIME_FAILURE` and no log file);
the user's normal terminal is unaffected.
