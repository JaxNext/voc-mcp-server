# 1.6 — Token refresh and 401 recovery (Task 6) Implementation Record

> Task 6 of [implementation-plan.md](implementation-plan.md), built against

> **Date:** 2026-09-30.
> **Status:** code complete and verified by tests + a running `wrangler dev`.

**Goal:** the long-lived behaviour of §7.3 — MCP clients hold a long-lived Worker token, so the
real Voc credential in `VOC_SESSIONS` must stay usable across the hour-scale expiry of Supabase
access tokens, and an unusable credential must force re-authentication rather than masquerade as
empty data.

Design choices worth noting:

- **The refresh runs in a preflight inside `vocApiHandler.fetch`, before the MCP dispatch.** A
  tool turns every error into an `isError: true` result (§9) and could never emit the
  `401` + `WWW-Authenticate` an expired Voc grant needs. So the api handler resolves the session
  first and only then builds `createServer` with the resolved `access_token` closed over. This is
  what makes "never degrade a 401 into empty results" structurally true, not conventional.
- **Identity is read from `ctx.props`, not `getMcpAuthContext()`.** `workers-oauth-provider`
  sets `ctx.props` from the decrypted grant immediately before dispatch
  (`oauth-provider.js` internal-token path ~line 3890, external-token path ~line 3940);
  `getMcpAuthContext()` only exists *inside* the dispatched handler, which is too late for a
  preflight. The global `ExecutionContext` type has no props, so the read is cast
  (`ProviderContext`).
- **`loadVocSession` is the single read path** for a request's Voc credential: no session →
  `VocSessionExpiredError`; token valid for more than 60s → returned as-is; otherwise refresh,
  persist the rotated pair, return it.
- **Any refresh failure clears KV and surfaces as re-authentication.** `loadVocSession` wraps
  non-`VocSessionExpiredError` failures and always `deleteVocSession`s. The api handler maps
  `VocSessionExpiredError` to `bearerChallenge(RESOURCE)` — the same 401 shape the provider's own
  `createBearerChallenge` produces, so a client treats an expired Voc grant exactly like a
  missing Worker token.
- **`fetchImpl` is injectable all the way down.** `createVocApiHandler({ fetchImpl })` feeds both
  the refresh POST and the `PostgrestClient`, so tests drive everything offline; production uses
  the global fetch (`vocApiHandler = createVocApiHandler()`).
- **Rotation accepted, escape hatch noted.** Supabase rotates the refresh token on use; two
  concurrent refreshes for one user can invalidate each other. For a single-user deployment this
  is a negligible race — accepted per §7.3, whose Durable Object (keyed by `voc_user_id`) escape
  hatch stays documented and unimplemented until it bites.

## Issues hit and how they were resolved

### 1. A tool cannot produce a 401

The Task 3 tools return `isError: true` results for every failure (by design, §9) — a revoked Voc
session inside a tool would surface as an error *result*, not an HTTP status, and the MCP
transport would answer `200`. The exit criterion ("revocation resolves by re-authentication")
requires a real `401`.

**Fix:** moved the session resolution into the api handler as a preflight, ahead of the dispatch.
The tools keep their error-as-result contract; the transport-level decision (re-auth vs. serve)
is made one layer up, where a `Response` is still in scope.

### 2. `ctx.props` typing

`createMcpHandler`'s handler signature takes the global `ExecutionContext`, which carries no
`props`. The provider sets it at runtime, so the read needs a cast.

**Fix:** a local `type ProviderContext = ExecutionContext & { props?: Partial<VocGrantProps> }`
and `(ctx as ProviderContext).props?.voc_user_id`. No dependency on an `authInfo` type the
package does not ship.

### 3. Refreshed token must reach the PostgREST client

`createServer(voc)` takes a `VocSessionFactory` that resolves *per tool call* (§8), but the token
is resolved once in the preflight. Re-loading inside the factory would double-refresh (and
re-rotate).

**Fix:** the factory closes over the preflight's resolved `session` and builds a fresh
`PostgrestClient` from `session.access_token` for each call — one refresh per request, a fresh
client per tool call.

## Deviations from the design doc

| § | Design said | Actual | Reason |
|---|---|---|---|
| §8 identity | "`authInfo.props` carries `voc_user_id`" | read from `ctx.props` in the api handler | `workers-oauth-provider` exposes no `authInfo` type; the provider sets `ctx.props` before dispatch (recorded in 1.5 too) |
| §9 | "Voc session expired → `isError: true`, plus a 401" | a single `401` + `WWW-Authenticate` from the preflight; the tool never runs | a tool's `isError` result is a `200` on the wire and cannot trigger re-auth — the two cannot coexist, and re-auth is the required recovery |
| §7.3 | refresh-token rotation "negligible race" | accepted as-is; DO escape hatch documented, not built | single-user deployment; matches §7.3's own guidance |
