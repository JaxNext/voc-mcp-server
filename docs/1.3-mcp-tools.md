Design choices worth noting:

- **`VocSessionFactory` dependency injection.** Tools never see OAuth. `createServer(voc)`
  takes a factory returning `{ client: PostgrestClient, userId: string }` per request. The
  dev wiring in `index.ts` builds it from the bearer token; Task 5 rebuilds it from
  `authInfo` + KV; tests stub it with a literal. One seam, three consumers.
- **Full `z.object(...)` for `inputSchema`.** The MCP SDK 2.0 raw-shape form
  (`{field: z.string()}`) is deprecated; each tool passes the Task 2 schema object directly.
  SDK 2.0 derives the handler arg type via `InferOutput`, so `args` is fully typed.
- **`list_tags` omits `inputSchema` entirely** for a no-input tool — SDK 2.0 accepts no
  schema and advertises `properties: {}`.
- **`formatSearchResult` owns the §9 "says so explicitly" duty:** header
  `Total matching records: N (page P).`, and when `total > shown` a closing line
  `Showing X of Y. Narrow the filters, raise the page, or increase pageSize to see the rest.`
- **`toErrorResult` is the single catch-all** each handler wraps its body in:
  `UnknownTagError` → "Unknown tag(s): X. Close matches: …. Use list_tags…",
  `PostgrestError` → "Voc request failed (HTTP <status>): …", anything else →
  "Unexpected error…". Not-found is handled *before* the catch via the `null` returns of
  Task 2's data layer, phrased as "Record <id> not found. Use search_records to find valid
  ids." — every message names a next step (§9).
- **Dev identity (Task-3-only):** on `/mcp` the bearer token **is** the caller's Voc JWT;
  `userId` = its `sub` claim decoded without verification (`decodeJwtSub`, base64url +
  `atob`). Documented in `index.ts` as scaffolding that Task 5's OAuthProvider replaces.
  PostgREST is only touched on `tools/call`, so `tools/list` works with any bearer — which
  is what makes the Inspector walkthrough possible today.

## Issues hit and how they were resolved

### 1. SDK 2.0's API shape differs from the docs everyone knows

`@modelcontextprotocol/server` 2.0.0 is a rewrite: package split into `core` + separate
`client` and `server` packages, `InMemoryTransport` exported from `server`, `registerTool`
taking `{ title, description, inputSchema, annotations }` with `inputSchema` as a full
`z.object`, handlers receiving `(args: InferOutput<…>, ctx)`. Resolved by reading the
installed `.d.ts` files (`agents/dist/mcp/server/*`, `server/dist/*.d.mts`) rather than
guessing from 1.x memory — same method as Task 1's `createMcpHandler` discovery.

### 2. Misplaced bottom imports (twice)

First drafts of `create-record.ts` and `list-tags.ts` accidentally had imports at the
bottom of the file (TS hoists them, but the diagnostic noise and style cost isn't worth
it). Both files rewritten with imports at top; `list-tags.ts` also dropped its
`inputSchema` in the same pass.

### 3. Test UUID violated RFC 4122 — again, one layer deeper this time

The first full-suite run failed 7 tests. Three symptoms, two causes:

- "Input validation error: Invalid arguments for tool get_record: id: Invalid UUID" —
  `RECORD_ID = 2222…-2222` in `test/tools.spec.ts` has the Task 2 lesson's exact flaw
  (`z.uuid()` requires the variant nibble ∈ [89ab]). It never bit Task 2 because row
  constants there never cross a Zod boundary; here the id is a *tool argument*, so the SDK
  rejects it before any handler code runs. Fixed to `22222222-2222-4222-8222-222222222222`
  with a comment pointing at the lesson.
- The create happy path asserted `requests[1]` was the `record_tags` insert, but
  `resolveTagNames` issues a `GET /tags` first, shifting positions. Fixed by locating the
  insert by method+table (`requests.find(POST && record_tags)`) instead of index —
  robust against ordering changes.

### 4. Unused `requestContext` param in the dev wiring

`createMcpHandler(requestContext => createServer(voc))` triggered
`'requestContext' is declared but its value is never read`. Under the dev wiring the
factory closes over the bearer token; the context's `authInfo` only exists under Task 5's
OAuthProvider. Dropped the param with a comment saying exactly that.

## Verification (exit criteria evidence)

| Criterion | Command | Result |
|---|---|---|
| Types clean | `pnpm typecheck` (`tsc --noEmit`, TS 7.0.2) | exit 0, no output |
| All tests green, offline | `pnpm test` (Workers pool) | **47 passed** — tools 13, records 15, search 10, tags 8, smoke 1 |
| Six tools over real HTTP | `wrangler dev` + curl `POST /mcp` (`initialize`, `tools/list`, bearer `dev-token`) | 200 SSE; exactly six tools, annotations per §6 |
| Unauthenticated rejected | same without `Authorization` | 401 |

The `tools/list` response over streamable HTTP confirmed, per tool: `title` + description
present; `readOnlyHint` true on `search_records`/`get_record`/`list_tags`, false elsewhere;
`destructiveHint` true only on `delete_record`; no `user_id` in any `inputSchema.properties`;
`list_tags` advertises `properties: {}`.

The InMemoryTransport suite additionally proves per-tool behavior the listing can't:
create resolves `['TRAVEL','work']` → tag UUIDs and runs the 3-step composite; unknown tags
error with close matches and **no writes** (all requests GET); search prints the total and
the "Showing 20 of 57" truncation note; get/update/delete return the exact structured
not-found message on `PGRST116`; update merges omitted fields and writes only the tag diff
(add `ID_WORK`, no delete); delete confirms with content + "cannot be recovered";
PostgREST 503 surfaces as an `isError` text result, not a throw.

**Remaining user step (documented, not blocking):** a real end-to-end `tools/call` with a
genuine Voc JWT needs the real Supabase URL + anon key in `.dev.vars` — Voc keeps no local
`.env`. Fill `.dev.vars`, `pnpm dev`, then e.g.:

```bash
curl -N -X POST http://127.0.0.1:8787/mcp \
  -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  -H "Authorization: Bearer <VOC_JWT>" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"list_tags","arguments":{}}}'
```

Or run MCP Inspector against `http://127.0.0.1:8787/mcp` and paste the JWT as the bearer.
